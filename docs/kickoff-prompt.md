# Стартовый промпт для новой сессии (ccguard)

Привет. Продолжаем ccguard — мой self-hosted EDR для AI-кодинг-агентов (Claude Code)
на developer-эндпоинтах. Контекст подробно в memory (project_edr_roadmap_2026_06 и
рядом) — подними и сверься, прежде чем предлагать.

ГЛАВНЫЙ ПРИНЦИП, от которого не отступаем: НИКАКИХ ДЕКОРАЦИЙ. Каждая фича должна
РЕАЛЬНО работать end-to-end и быть проверена — а не «выглядеть как будто работает».
Если что-то нарисовано в UI, но не подключено к движку; если детектор зарегистрирован,
но никогда не стрелял; если кнопка есть, но ничего не делает; если индикатор показан,
но не гейтит — это декорация, и я её не хочу. Лучше меньше, но по-настоящему. Я уже
обжигался на «security-софте, который на деле не защищает» (история с Sakura VPN) —
ccguard не должен быть таким.

К ЧЕМУ СТРЕМЛЮСЬ: это НЕ игрушка. Я целюсь продавать это как продукт (SaaS / on-prem),
аудитория — вайбкодеры и AppSec/SOC в финтехе/healthtech, которым классический EDR
(CrowdStrike/SentinelOne) и cloud-AI-WAF (Lakera/Cisco) не закрывают слепое пятно:
shell-execution через AI dev-tooling. Мой МОАТ: ccguard видит AI-origin триггер
(prompt-injection / подмена-или-новый MCP / tool-poisoning / context-poisoning) И
связывает его с последующей endpoint kill-chain (доступ к секрету → вынос) как ОДНУ
историю — то, что per-endpoint EDR структурно не может агрегировать. Этот тезис должен
быть правдой целиком и быть ВИДЕН в продукте, а не только в коде.

ЧТО ЦЕНЮ В РАБОТЕ:
- Сильный детект (поведенческие IOA > атомарные IOC, они протухают), FP-safe by
  construction, дисциплина «лови abuse-инвокацию, не голый бинарь».
- Блокировать очевидно-злое из коробки (hard_deny, переживающий observe), а не только
  смотреть. И сам ccguard нельзя выключить одной командой агента (anti-tamper).
- Методология, которая мне зашла: research/red-team воркфлоу (агенты читают РЕАЛЬНЫЙ
  код / ходят в источники типа GTFOBins/LOLBAS/ATT&CK) → детерминированный eval против
  настоящего extract_signals/decide (агенты преувеличивают — код проверяет) → системные
  фиксы → корпус-гард в CI. 0 новых FP на benign-корпусах.
- TDD, регресс зелёный после каждого куска, коммит по завершении куска. Работаем ПРЯМО
  в master, без feature-веток — я доверяю.
- UI должен ОТВЕЧАТЬ на вопрос «эта машина скомпрометирована прямо сейчас?» и давать
  провалиться в находку (цепочка нарисована, вся метадата, кликабельно для отладки).
- Стек не меняем (Python 3.12 / FastAPI / SQLModel / HTMX+Jinja2 / SQLite-WAL),
  всё on-prem, единственная внешняя зависимость — Anthropic API (опциональный).

КАК РАБОТАТЬ СЕЙЧАС: я часто говорю «делай сам / катим дальше» — бери инициативу,
закрывай чистые высокоценные куски, а на трейдоффах (FP-калибровка, продуктовые
развилки) — спрашивай коротко (можно AskUserQuestion, мне удобно тапать с телефона).
Перед заявлением «X не покрыто/сломано» — проверь по коду, не спекулируй. Когда что-то
сделано — проверь вживую (тесты + при UI-изменениях скриншоты), и скажи прямо без хеджа.

Открытые направления (мой выбор приоритета каждый раз): docker/kubectl-exec и cloud-IAM
глубже · context-poisoning через Write-tool (не только Bash echo) · последняя миля
(триаж находок ack/close + observe-баннер «вас НЕ защищают») · push-алертинг (канал
решим) · interpreter-aware round 2 (path-join/sed) · оживить авто-обогащение сигналов
(source_monitors + SignalDrafter дремлют). Но сначала подними память и предложи, с чего
начать, исходя из «никаких декораций» и «это надо продавать».
