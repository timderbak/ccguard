# Ревью продукта: спека «EDR уровня агента» vs. реальный ccguard

> Снимок на 2026-06-06. Строгий gap-анализ: что декларирует целевая спецификация «Endpoint Detection & Response для AI-агентов» и что реально стоит в коде. Без натягиваний. Факты сверены с кодовой базой.

## Проверенные точки (основа выводов)

- `eBPF`/syscall/`connect()`-перехват — **ноль** упоминаний в `src/`.
- `session_id` присутствует только во входе PreToolUse-хука (`schemas/enforce.py:19`); в `ToolUseEvent`/audit **не персистится**. Корреляция идёт по `machine_id`, не по сессии.
- `sequence_service` — один паттерн `cred.read.* → egress.*` в окне времени на одной машине.
- LLM-сканер защищён `tool_use` со `strict`-схемой (`report_risk`), но **без** явной анти-инъекционной рамки в `SYSTEM_PROMPT` и без dual-LLM.
- Активного finding'а на «сенсор замолчал / shim подменён» нет — только `last_seen` и UI-бейдж last-sync.
- Транспорт MCP различается (stdio/http/sse — `agent/scan/mcp.py:38`).

## Что спека требует и что в продукте УЖЕ есть

Совпадает хорошо: inventory с хешем **фактического** содержимого (§4), TOFU-drift для MCP/hook/skill/agent (§5.1, 5.2), LLM-скан скиллов/агентов с `quoted_snippet` (§5.3), опасный bash (§5.4), сетевые сигналы из парсинга bash-URL (§5.5), PI в Read (§5.6), observe/enforce (§7), NFR по латентности/хешам/backward-compat (§10). Это слой A целиком и движки 5.1–5.6.

---

## 1. Слой B (eBPF) отсутствует полностью — а спека объявляет его половиной продукта

Спека: «Связка слоёв = суть продукта» (§3.1). В коде — ноль eBPF. Из этого выпадает всё, что на нём держится:

- **Агент-агностичность (§3.2)** — нет. Виден только Claude Code через хуки. Cursor/Codex/Cline/самописные = невидимы.
- **Видимость local stdio MCP-процессов** — спека (§1, §8) называет это «уникальным, что отдаёт EDR». Сейчас stdio-MCP виден только как **строка конфига** при инвентаре, но не его фактические syscalls/egress во время работы. Слепое пятно, ради которого продукт позиционируется, не закрыто на уровне исполнения — только на уровне инвентаря.
- **`connect()` мимо bash (§5.5)** — нет. Сетевой детект работает только если egress идёт через распарсенную bash-команду. `curl` внутри MCP-сервера или Python-subprocess агента — мимо.

Не «частично», а 0%. Самый большой структурный разрыв.

## 2. Корреляция (§6) — заявлена «главным множителем ценности», построена на ~15%

В продукте — `sequence_service`: один паттерн `cred.read.* → egress.*` в окне на одной машине. Не реализовано:

- **Корреляция из 4 источников (§6.2).** Источник по сути один — сигналы из хуков. Нет MCP-хаба и LLM-gateway как входов, нет слоя B. «Единая timeline по сессии» из четырёх потоков не существует.
- **Флагманский пример самой спеки — `injection→action` (§6.2/6.3)**: «прочитал внешний README → вызвал ненужный инструмент → записал в скрытый файл → открыл соединение». Эта kill chain — витрина продукта — не построена. Есть только recon→exfil без среднего звена и без привязки к прочитанному контенту.
- **Сессионная гранулярность.** `session_id` приходит в PreToolUse, но не персистится и не используется. Вся детекция machine-scoped; два параллельных проекта одного юзера сольются в один поток.
- **Паттерны §6.3** кроме recon→exfil (`poisoned-tool→legit-execution`, объём/частота, время/контекст) — не реализованы как корреляционные правила.

Вывод: то, что спека продаёт как ядро, в продукте — простейший двухшаговый детектор на одном слое.

## 3. Самозащита сенсора / heartbeat-алерт (§5.7, §9) — пассивная, не детект

Спека: «если агент перестал слать sync или shim подменён — сервер алертит». В коде нет эмиттера finding'а на «машина замолчала» — только `last_seen` и UI-бейдж. Это отображение, а не детекция: никто не сработает, если сенсор тихо умер. Отключаемый без алерта сенсор — дыра, которую спека явно называет обязательной к закрытию.

## 4. SIEM-экспорт (§8) — отсутствует

OTel/syslog-экспорт с нормализованной схемой (agent_id, session_id, correlation_id, вердикт) — нет (известный deferred, Phase 6 roadmap). Раз спека строит на этом позиционирование «EDR-сенсор для SOC-мозга» — оно пока не подкреплено. Плюс: экспортировать `correlation_id`/`session_id`, которых в данных нет (п.2), нечем.

## 5. Защита самого LLM-сканера (§5.3) — частично

Структурная защита есть — `tool_use` со `strict`-схемой не даёт вернуть произвольное «verdict: safe» прозой. Но явной анти-инъекционной рамки в `SYSTEM_PROMPT` нет (он описывает роль классификатора, не предупреждает про вложенные инструкции), dual-LLM нет. Для скана заведомо недоверенного контента — половина защиты.

## 6. LLM-скан описаний MCP при первом заносе (§5.1) — похоже, не подключён

LLM-скан заведён для skills/agents; что он гоняется по MCP `description` — в коде не прослеживается. Если так — отравленное MCP-описание ловится только хешем при последующем drift, но не на входе.

## Сводка дельты

| Раздел спеки | Статус в ccguard |
|---|---|
| Слой A (хуки) | ✅ есть |
| Слой B (eBPF) | ❌ 0% |
| Inventory фактического содержимого | ✅ есть |
| Движки 5.1–5.6 (drift/skill-скан/bash/сеть/PI) | ✅ есть |
| 5.7 самозащита сенсора + heartbeat-алерт | ⚠️ пассивный бейдж, не детект |
| §6 корреляция (4 источника, session-timeline, injection→action) | ⚠️ ~15%, один паттерн, machine-scoped |
| §3.2 мульти-агентность | ❌ только Claude Code |
| §8 SIEM-экспорт | ❌ нет |
| 5.3 защита сканера | ⚠️ структурно да, промпт-изоляция/dual-LLM нет |
| 5.1 скан MCP-описаний на входе | ⚠️ вероятно нет |

**Одной фразой:** ccguard сегодня — качественно сделанный слой A + TOFU-инвентарь (движки 5.1–5.6 реальны и работают), но три несущих опоры спеки — eBPF-слой B, многоисточниковая корреляция в session-timeline и самозащита/экспорт — либо отсутствуют, либо реализованы как простейший частный случай. Разрыв не косметический: именно эти три вещи отличают «EDR уровня агента» от «набора регексов и хешей с UI».

## Оценка стоимости закрытия (грубо)

- **Дёшево, в текущем стеке:** heartbeat-алерт (finding при stale `last_seen`); персист `session_id` в `ToolUseEvent` + session-scoped корреляция; правило `injection→action`; анти-инъекционная рамка в `SYSTEM_PROMPT` сканера; LLM-скан MCP-описаний на входе; SIEM-экспорт (OTel/syslog).
- **Большой отдельный трек:** eBPF-слой B (новый сенсор, ядро, packaging, overhead) и, как следствие, агент-агностичная мульти-агентность.
